# FastAPI JWT Authentication

A production-oriented authentication backend built with FastAPI. It provides user registration, secure password storage, JWT access tokens, protected endpoints, database persistence, schema migrations, centralized configuration, and automated authentication tests.

## Features

- User registration and authentication
- JWT bearer access tokens
- Secure one-way password hashing
- Protected user endpoints
- Persistent user storage with SQLAlchemy
- Database migrations with Alembic
- Environment-based configuration
- Request and response validation with Pydantic
- Interactive OpenAPI documentation
- Automated tests with pytest

## Technology Stack

- **API:** FastAPI
- **Server:** Uvicorn
- **ORM:** SQLAlchemy
- **Migrations:** Alembic
- **Validation and configuration:** Pydantic / pydantic-settings
- **Authentication:** OAuth2 password flow with JWT bearer tokens
- **Password security:** Passlib, pwdlib, bcrypt, or Argon2 depending on the installed implementation
- **Testing:** pytest and FastAPI TestClient or HTTPX

## Getting Started

### Prerequisites

- Python 3.11 or later
- pip or another Python package manager
- A supported relational database

SQLite can be used for local development. PostgreSQL is recommended for production deployments.

### 1. Clone the Repository

bash
git clone <repository-url>
cd <repository-directory>


### 2. Create a Virtual Environment

bash
python -m venv .venv


Activate it:

bash
# Linux or macOS
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1


### 3. Install Dependencies

bash
pip install --upgrade pip
pip install -r requirements.txt


## Configuration

Create a `.env` file in the project root. Do not commit this file.

env
APP_NAME=FastAPI JWT Authentication
ENVIRONMENT=development
DEBUG=true

DATABASE_URL=sqlite:///./app.db

SECRET_KEY=replace-with-a-long-random-secret
JWT_ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30


For PostgreSQL, use an appropriate SQLAlchemy URL, for example:

env
DATABASE_URL=postgresql+psycopg://app_user:strong_password@localhost:5432/app_db


Generate a cryptographically secure secret key with:

bash
python -c "import secrets; print(secrets.token_urlsafe(64))"


### Configuration Reference

| Variable | Description | Example |
|---|---|---|
| `APP_NAME` | Application name | `FastAPI JWT Authentication` |
| `ENVIRONMENT` | Runtime environment | `development` |
| `DEBUG` | Enables development diagnostics | `false` |
| `DATABASE_URL` | SQLAlchemy database connection URL | `sqlite:///./app.db` |
| `SECRET_KEY` | Secret used to sign JWTs | Random 64-byte value |
| `JWT_ALGORITHM` | JWT signing algorithm | `HS256` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Access token lifetime | `30` |

Configuration names may be adjusted to match the settings class used by the application.

## Authentication Flow

1. A client registers a user with an email or username and password.
2. The password is validated and stored only as a secure hash.
3. The client submits credentials to the login endpoint.
4. Valid credentials produce a signed JWT access token.
5. The client sends the token in the `Authorization` header when accessing protected endpoints.
6. The API validates the token signature, expiration, and subject before loading the authenticated user.

http
Authorization: Bearer <access-token>


Passwords are never included in API responses or stored as plaintext.

## API Endpoints

Common authentication endpoints are listed below. Confirm the exact paths in the generated OpenAPI documentation.

| Method | Endpoint | Authentication | Description |
|---|---|---:|---|
| `POST` | `/auth/register` | No | Register a user |
| `POST` | `/auth/login` | No | Authenticate and obtain an access token |
| `GET` | `/users/me` | Bearer token | Return the current user |
| `GET` | `/health` | No | Application health check, if configured |

### Register a User

bash
curl -X POST http://127.0.0.1:8000/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "CorrectHorseBatteryStaple!"
  }'


Example response:


{
  "id": 1,
  "email": "user@example.com",
  "is_active": true
}


### Log In

OAuth2 password flow commonly expects form-encoded credentials:

bash
curl -X POST http://127.0.0.1:8000/auth/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=user@example.com&password=CorrectHorseBatteryStaple!"


Example response:


{
  "access_token": "<signed-jwt>",
  "token_type": "bearer"
}


If the implementation accepts JSON credentials instead, send the email and password with `Content-Type: application/json`. The OpenAPI documentation reflects the configured request format.

### Access a Protected Endpoint

bash
curl http://127.0.0.1:8000/users/me \
  -H "Authorization: Bearer <signed-jwt>"


## JWT Claims

Access tokens should contain only the minimum required claims. Typical claims include:

- `sub`: Stable user identifier
- `iat`: Token issue time
- `exp`: Token expiration time
- `type`: Optional token type discriminator

JWT payloads are encoded and signed, not encrypted. Never place passwords, secrets, or sensitive personal data in a token.

## Testing

Run the complete test suite:

bash
pytest


Run with verbose output and coverage:

bash
pytest -v --cov=app --cov-report=term-missing


Authentication tests should cover at least:

- Successful user registration
- Duplicate registration rejection
- Password policy validation
- Successful login
- Invalid credential rejection
- Access with a valid token
- Missing bearer token rejection
- Malformed token rejection
- Expired token rejection
- Unknown or inactive user rejection
- Password hashes not being exposed in responses

Tests should use an isolated database and must not modify development or production data.

## Common HTTP Responses

| Status | Meaning |
|---:|---|
| `200 OK` | Login or protected resource request succeeded |
| `201 Created` | User registration succeeded |
| `400 Bad Request` | Request violates an application rule |
| `401 Unauthorized` | Credentials or access token are invalid |
| `403 Forbidden` | Authenticated user lacks permission or is inactive |
| `409 Conflict` | Email or username is already registered |
| `422 Unprocessable Entity` | Request validation failed |

Actual status codes depend on the route implementation.

## Security Considerations

- Store `SECRET_KEY` in a secret manager in production.
- Never commit `.env`, database credentials, private keys, or generated tokens.
- Use HTTPS for all non-local traffic.
- Use a modern adaptive password hashing algorithm and an appropriate work factor.
- Return generic login errors to avoid account enumeration.
- Keep access tokens short-lived.
- Validate JWT signature, algorithm, expiration, issuer, and audience when configured.
- Do not trust an algorithm supplied only by the token header.
- Consider refresh-token rotation and revocation for long-lived sessions.
- Add rate limiting to registration and login endpoints.
- Restrict CORS to known origins.
- Record security-relevant events without logging passwords or tokens.
- Keep dependencies updated and run vulnerability scans in CI.
- Back up the production database and test restoration procedures.

## Production Checklist

Before deployment:

1. Set `DEBUG=false`.
2. Replace the development secret with a strong production secret.
3. Configure PostgreSQL or another production-grade database.
4. Apply Alembic migrations as a controlled deployment step.
5. Enable HTTPS at the reverse proxy or load balancer.
6. Restrict allowed hosts and CORS origins.
7. Configure structured logging and monitoring.
8. Run the test suite and dependency security checks.
9. Use separate secrets and databases for every environment.
10. Define a key-rotation and token-revocation strategy.

## Troubleshooting

### Migration errors

Confirm that `DATABASE_URL` is valid and the database is reachable, then run:

bash
alembic current
alembic upgrade head


### `401 Unauthorized` on protected routes

Verify that:

- The header uses `Authorization: Bearer <token>`.
- The token has not expired.
- The signing secret and algorithm match those used to issue the token.
- The user referenced by the token still exists and is active.

### Password hashing backend errors

Ensure the password hashing library and its required backend are installed from `requirements.txt`. Reinstall dependencies inside a clean virtual environment if native or binary packages are inconsistent.
